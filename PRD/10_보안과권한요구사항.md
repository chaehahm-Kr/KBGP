---
문서: 10. 보안과 권한 요구사항
---

# 이 문서의 목적

여기 적힌 항목들은 "나중에 여유 있으면 하는 것"이 아니라, **B2B 플랫폼이라면 처음부터 지켜야 하는 최소 기준**입니다. 회사의 사업자 정보, 인증서, 성분표, 향후에는 계약서와 결제 정보까지 오가는 시스템이므로, 보안 사고가 나면 신뢰 자체가 무너집니다 — 이 플랫폼이 마케팅 사이트에서부터 강조해온 "신뢰"라는 핵심 가치와 직결됩니다.

# 1. 데이터 격리 (가장 중요)

- **회사 간 데이터는 물리적으로도, 논리적으로도 완전히 분리되어야 합니다.** A회사 담당자가 어떤 경로로도(직접 URL 입력, 개발자도구 조작 등) B회사의 신청서·제품·문서를 볼 수 없어야 합니다.
- 이를 위해 서버가 데이터를 내려줄 때마다 "이 요청을 보낸 사람이 정말 이 데이터의 소속 회사 사람인가"를 매번 확인하는 절차가 있어야 합니다. 화면에서 메뉴를 숨기는 것만으로는 부족합니다 — 주소를 직접 입력해도 막혀야 합니다.
- 내부 메모, 심사 기준 상세 등 "외부 비공개" 데이터는 애초에 외부용 화면·기능에서 조회하는 경로 자체가 존재하지 않아야 합니다.

# 2. 인증(로그인) 요구사항

- 비밀번호는 최소 길이와 조합 규칙을 강제합니다(예: 8자 이상, 영문+숫자 조합).
- 비밀번호는 평문으로 저장하지 않고, 되돌릴 수 없는 방식으로 암호화해 저장합니다 — 이건 기술적으로 표준적인 방식이라 개발 시 자연스럽게 적용됩니다.
- 로그인 5회 연속 실패 시 일정 시간 잠금(예: 15분) 처리해 무작위 대입 공격을 막습니다.
- 비밀번호 재설정 링크는 1회용이며 짧은 시간(예: 30분) 안에만 유효합니다.
- 내부 직원(관리자 포털) 로그인은 외부 파트너 포털과 **완전히 다른 로그인 경로**를 사용합니다. 같은 로그인 화면에서 역할에 따라 분기하는 방식은 피합니다 — 실수로라도 잘못된 포털로 진입하는 사고를 구조적으로 막기 위함입니다.
- (권장, Phase 2 이후 검토) 내부 직원 계정에는 2단계 인증(이메일 또는 OTP)을 적용하는 것을 권장합니다. 회사 자산(제품 정보, 계약 조건 등)을 다루는 계정이므로 일반 소비자 서비스보다 높은 수준을 권장합니다.

# 3. 권한(Authorization) 요구사항

- `02_사용자유형과권한표.md`에 정의된 역할별 권한을 서버 쪽에서 강제합니다. 화면에 버튼을 안 보이게 하는 것은 사용자 경험을 위한 것이고, 실제 차단은 서버가 매 요청마다 권한을 재확인해야 합니다.
- 권한 확인 실패 시 오류 메시지에 "왜 안 되는지"를 너무 자세히 알려주지 않습니다(예: "이 회사의 신청서가 아닙니다" 대신 "접근 권한이 없습니다" 수준으로). 너무 상세한 오류는 공격자에게 힌트를 줄 수 있습니다.
- 계정이 비활성화(퇴사 처리 등)되면 **즉시** 모든 로그인 세션이 무효화되어야 합니다. "다음 로그인부터 차단"이 아니라 "지금 로그인되어 있어도 즉시 튕겨나감"이어야 합니다.

# 4. 파일 보안

- 업로드된 파일(인증서, 성분표, 계약서 등)은 직접 URL로 접근할 수 없고, 반드시 로그인+권한 확인을 거쳐야만 열람 가능합니다. (`09_알림및문서관리규칙.md`와 연결)
- 파일 업로드 시 파일 내용이 실제로 신고된 형식과 일치하는지 확인합니다(확장자만 바꾼 악성파일 방지).

# 5. 개인정보·사업자정보 보호

- 이 시스템이 다루는 민감 정보: 담당자 개인 연락처, 사업자등록번호, (향후) 계약 조건·가격 정보, (향후) 결제 관련 참고 정보.
- 사업자등록번호 등은 목록 화면에서 전체 노출보다 일부 마스킹 표시를 권장합니다(상세 화면 진입 시에만 전체 표시).
- 회사가 탈퇴/계정 삭제를 요청할 경우의 처리 정책을 미리 정해두는 것을 권장합니다 — 완전 삭제는 어렵습니다(이미 진행된 신청·계약 이력은 법적·회계적 이유로 보존해야 할 수 있음). "비활성화 + 접근 차단, 데이터는 보관"을 기본 정책으로 제안합니다. 정확한 처리는 개인정보 관련 법률 자문을 받아 확정하시길 권장합니다(이 부분은 제가 법률 전문가가 아니므로 참고용 제안입니다).

# 6. 변경 이력 추적 (Audit Trail)

- 상태값이 바뀌는 모든 행동(심사 결과, PO 승인, 결제 상태 변경 등)은 "누가, 언제, 무엇을 어떻게 바꿨는지"가 `ActivityLog`에 남아야 합니다(`07_데이터모델.md` 참고).
- 이 로그는 수정·삭제가 불가능해야 합니다(추가만 가능). 나중에 분쟁이 생겼을 때("승인한 적 없다" 등) 이 로그가 유일한 객관적 증거가 됩니다.

# 7. 통신 보안

- 모든 페이지와 API 통신은 암호화된 연결(HTTPS)만 허용합니다. 이건 요즘 웹 서비스의 기본값이라 대부분 자동으로 적용되지만, 개발 완료 후 반드시 확인 항목에 넣습니다.

# 8. Phase별 보안 강화 로드맵

| Phase | 최소 요구 | 권장(여유 있으면) |
|---|---|---|
| 1 | 데이터 격리, 기본 인증, 파일 접근 제어, 변경 이력 | 로그인 시도 제한 |
| 2 | 위 전체 + 계약서 등 민감문서 접근 로그 별도 기록 | 내부 직원 2단계 인증 |
| 3 | 위 전체 + 결제 관련 정보 취급 시 추가 마스킹, 리테일러 계정 격리(회사 계정과 동일 수준) | 정기 보안 점검(외부 점검 포함 검토) |

# 9. 이 문서에서 다루지 않은 것

PCI-DSS(카드결제 보안 인증) 같은 결제 관련 보안 표준은 다루지 않습니다 — 확정 답변에서 이 시스템은 실제 결제를 처리하지 않기로 했기 때문입니다. 만약 나중에 온라인 결제 기능을 추가하기로 결정이 바뀌면, 이 문서를 그때 별도로 확장해야 합니다.
