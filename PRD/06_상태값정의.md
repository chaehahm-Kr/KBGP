# 용어 안내

**상태값(Status)**이란 "지금 이 건이 전체 과정 중 어디에 와 있는가"를 나타내는 딱지입니다. 상태값을 미리 정해두면, 화면에서 필터링하고("심사중인 것만 보여줘"), 자동 알림을 보내고("승인되면 이메일 발송"), 통계를 낼 수 있습니다("이번 달 승인률").

**상태 전이(State Transition)**란 "이 상태에서 다음에 어떤 상태로 갈 수 있는가"의 규칙입니다. 예를 들어 "반려" 상태에서 갑자기 "승인"으로 바로 못 가게 막는 것도 상태 전이 규칙입니다.

# 1. 신청 상태값 (Application Status) — Phase 1

신청서 **전체**의 상태입니다. 안에 포함된 개별 제품 상태와는 별개입니다.

| 상태 | 의미 | 누가 바꾸나 |
|---|---|---|
| `임시저장` | 회사가 작성 중이며 아직 제출 전 | 회사 |
| `제출됨` | 회사가 제출 완료, 담당자 배정 전 | 시스템(자동) |
| `배정됨` | 담당자가 배정됨, 아직 심사 시작 전 | 관리자 |
| `심사중` | 담당자가 서류·제품을 검토하는 중 | 관리자 |
| `추가자료요청` | 부족한 자료가 있어 회사의 회신을 기다리는 중 | 관리자 |
| `재검토중` | 회사가 추가 자료를 제출해 다시 심사 중 | 시스템(자동, 회사 제출 시) |
| `부분승인` | 신청서 안 일부 제품만 승인됨 | 시스템(자동, 제품별 심사 결과 집계) |
| `승인` | 신청서 안 모든 제품이 승인됨 | 시스템(자동) |
| `보류` | 지금 시점에는 진행이 어렵다는 판단(거절이 아니라 "아직 아니다") | 관리자 |
| `반려` | 참여 조건 미충족 등으로 진행 불가 | 관리자 |
| `취소` | 회사가 스스로 신청을 철회 | 회사 |

## 상태 전이 규칙

```
임시저장 → 제출됨 → 배정됨 → 심사중 ──┬──► 추가자료요청 → 재검토중 → 심사중 (반복 가능)
                                      │
                                      ├──► 부분승인 / 승인 / 보류 / 반려
                                      │
                                      └──► (회사가 취소 요청 시) 취소
```

- `보류`와 `반려`에서 새 신청서를 다시 낼 수는 있지만(재신청), **기존 신청서 자체가 다시 `승인`으로 바뀌지는 않습니다.** 재도전은 항상 새 신청서로 합니다. 이렇게 해야 "몇 번째 시도인지" 이력이 깨끗하게 남습니다.
- `부분승인` `승인` `보류` `반려`는 **되돌릴 수 없는 종료 상태**가 아니라, 관리자가 재심사 사유가 있으면 `심사중`으로 되돌릴 수 있어야 합니다(예: 심사자 실수 정정). 단 이 경우 반드시 사유를 내부 메모에 남기도록 강제합니다.

# 2. 제품 심사 상태값 (Product Review Status) — Phase 1

신청서 안에 포함된 **제품 하나하나**의 상태입니다. (정확히는 "이 신청서 맥락에서 이 제품"의 상태 — 데이터 모델에서는 `ApplicationProduct`에 저장됩니다. `07_데이터모델.md` 참고)

| 상태 | 의미 |
|---|---|
| `검토대기` | 신청서에 포함됐지만 아직 담당자가 이 제품을 보지 않음 |
| `검토중` | 담당자가 이 제품을 보고 있음 |
| `보완요청` | 이 제품에 대해서만 추가 정보 필요(예: 성분표 재제출) |
| `승인` | 이 제품은 파트너십 진행 가능 |
| `보류` | 지금은 아니지만 나중에 재검토 가능 (예: "300개 테스트 판매 데이터가 더 필요") |
| `반려` | 이 제품은 진행 불가 (예: 인증 요건 미충족) |

## 상태 전이 규칙

```
검토대기 → 검토중 ──┬──► 보완요청 → (자료 재제출 시) 검토중
                    │
                    └──► 승인 / 보류 / 반려
```

## 신청 상태와 제품 심사 상태의 관계 (자동 집계 규칙)

신청서 전체 상태는 안에 포함된 제품들의 심사 상태를 보고 **시스템이 자동으로 계산**합니다. 관리자가 매번 손으로 "전체 승인" 버튼을 누르는 대신, 아래 규칙을 적용합니다.

- 포함된 제품이 **전부 승인** → 신청 상태 `승인`
- 포함된 제품 중 **일부만 승인**, 나머지는 반려/보류 → 신청 상태 `부분승인`
- 포함된 제품이 **전부 반려** → 신청 상태 `반려`
- 포함된 제품이 **전부 보류** (반려는 없음) → 신청 상태 `보류`
- 하나라도 아직 `검토중`/`보완요청`이면 신청 상태는 `심사중`/`추가자료요청` 유지

> 이 자동 집계 규칙은 제가 판단으로 설계한 부분입니다. 실제 운영 방식과 다르면 알려주세요 — 예를 들어 "제품이 5개 중 1개라도 반려면 신청서 전체를 반려로 본다"처럼 더 엄격하게 갈 수도 있습니다.

# 3. 샘플 상태값 (Sample Status) — Phase 2

| 상태 | 의미 |
|---|---|
| `요청됨` | Letusto 또는 회사가 샘플 필요 표시 |
| `발송준비중` | 회사가 샘플을 준비/포장 중 |
| `발송됨` | 회사가 발송 완료, 운송장번호 입력 |
| `수령완료` | Letusto가 수령 확인 |
| `평가중` | 매장 테스트·품질 확인 진행 중 |
| `평가완료-긍정` | 다음 단계(견적)로 진행 가능 |
| `평가완료-보류` | 문제 발견, 개선 후 재발송 필요 |
| `분실/파손` | 예외 상황 — 배송 중 문제 발생 |

## 상태 전이 규칙

```
요청됨 → 발송준비중 → 발송됨 → 수령완료 → 평가중 ──┬──► 평가완료-긍정 → (견적 흐름으로)
                                                    └──► 평가완료-보류 → (재발송 시) 발송준비중으로 복귀

발송됨 → 분실/파손 (예외, 언제든 발생 가능 → 재발송 처리로 복귀)
```

# 4. 견적 상태값 (Quote Status) — Phase 2

| 상태 | 의미 |
|---|---|
| `준비중` | Letusto가 견적 작성 중 |
| `발송됨` | 회사에 견적 전달 완료 |
| `협상중` | 회사가 조건 변경 요청 |
| `수정발송` | 조건 반영해 재발송 |
| `승인됨` | 회사가 최종 승인 → 계약 단계로 |
| `거절됨` | 회사가 조건 거부 |
| `만료됨` | 유효기간(예: 발송 후 30일) 초과, 자동 처리 |

## 상태 전이 규칙

```
준비중 → 발송됨 ──┬──► 승인됨 → (계약 흐름으로)
                  ├──► 협상중 → 수정발송 → (다시 협상중 또는 승인됨/거절됨)
                  ├──► 거절됨
                  └──► (유효기간 초과 시 자동) 만료됨
```

# 5. PO 상태값 (Purchase Order Status) — Phase 2

거래 구조상 **Letusto가 발행 주체(매입자), 브랜드사(공급사)가 확인·승인 주체**입니다.

| 상태 | 의미 |
|---|---|
| `작성중` | 운영 담당자가 PO 초안 작성 |
| `내부승인대기` | Letusto 내부 결재 대기 (Super Admin 승인 필요) |
| `발행됨` | PDF 생성 및 공급사에 이메일 발송 완료 |
| `공급사확인대기` | 공급사의 승인/이의제기를 기다리는 중 |
| `확정` | 공급사가 승인, 양측 모두 확정 |
| `변경요청` | 공급사가 조건에 이의 제기 |
| `재발행` | 변경 반영 후 다시 발행 |
| `취소` | 발주 자체가 취소됨 |
| `이행완료` | 흐름 3(생산~배송)까지 모두 끝나 종료 |

## 상태 전이 규칙

```
작성중 → 내부승인대기 → 발행됨 → 공급사확인대기 ──┬──► 확정 → (생산 흐름 시작) → 이행완료
                                                  └──► 변경요청 → 재발행 → 공급사확인대기 (반복 가능)

작성중/내부승인대기/발행됨 → 취소 (언제든 가능, 사유 필수)
```

# 6. 주문 및 배송 상태값 (Order & Fulfillment Status) — Phase 3

PO가 `확정`된 이후, 하나의 PO 라인아이템(또는 전체 PO)이 실제로 이동하는 과정입니다.

| 상태 | 의미 |
|---|---|
| `생산대기` | PO 확정, 아직 생산 시작 전 |
| `생산중` | 공급사가 생산 진행 |
| `생산완료` | 생산 종료, 검사 대기 |
| `검사중` | 품질 검사 진행 |
| `검사통과` | 검사 합격 |
| `검사불합격` | 불합격 → 재작업 필요 (예외 처리) |
| `출고준비` | 포장·서류(Invoice, Packing List, BOL) 준비 |
| `출고완료` | 한국에서 선적/발송 완료 |
| `운송중` | 국제 운송 진행 중 |
| `통관중` | 미국 세관 통관 진행 중 |
| `미국입고완료` | 미국 창고 또는 매장에 도착 확인 |
| `지연` | 예외 — 예정일 초과, 원인 기록 필요 |
| `반품` | 예외 — 품질 문제 등으로 반송 |

## 상태 전이 규칙

```
생산대기 → 생산중 → 생산완료 → 검사중 ──┬──► 검사통과 → 출고준비 → 출고완료 → 운송중 → 통관중 → 미국입고완료
                                        └──► 검사불합격 → (재작업 후) 생산중으로 복귀

모든 단계 → 지연 (예정일 초과 시 자동 플래그, 상태 자체는 유지하되 경고 표시)
운송중/통관중/미국입고완료 이전 → 반품 (예외 처리, 사유 필수)
```

# 상태값 설계에서 지킨 공통 원칙

1. **모든 "부정적" 상태(반려, 거절, 취소, 반품)는 사유 입력을 필수로 강제합니다.** 나중에 왜 그런 결정을 했는지 반드시 추적 가능해야 합니다.
2. **"보류"는 "반려"와 다릅니다.** 이 구분은 마케팅 사이트에서 이미 강조한 "지금은 진출하지 마십시오"라는 정직한 진단의 철학을 그대로 이어받은 것입니다. 보류는 관계의 끝이 아니라 잠정 중단입니다.
3. **자동으로 바뀌는 상태와 사람이 눌러서 바뀌는 상태를 구분했습니다.** 위 표의 "누가 바꾸나" 열이 그 기준입니다. 자동 전이는 나중에 개발 명세서에서 "이 이벤트가 발생하면 상태를 바꿔라"는 규칙으로 그대로 옮겨집니다.
