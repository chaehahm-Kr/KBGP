# 이 문서의 역할

지금까지의 문서(00~10)는 **무엇을, 왜, 어떤 규칙으로** 만들지를 정한 기획서입니다. 이 문서는 그것을 실제로 개발할 때 **어떤 순서로, 몇 개의 작업 단위로** 나눌지를 정합니다. 여기서도 아직 코드나 기술 스택은 다루지 않습니다 — "개발 명세서"란 Claude Code에게 한 번에 넘길 작업 덩어리의 목록이지, 그 안에 들어갈 실제 코드가 아닙니다.

각 명세서를 실제로 작성할 때(=Claude Code에게 넘기기 직전)는, 이전에 마케팅 사이트 작업에서 보여드린 형식처럼 "무엇을 만들지 + 완료 조건 체크리스트 + 하지 말아야 할 것"을 갖춘 구체적인 프롬프트로 발전시키는 것을 권장합니다. 이 문서는 그 전 단계, 즉 "그 프롬프트 몇 개를 어떤 순서로 만들 것인가"에 대한 지도입니다.

# 1. 개발 우선순위 — 큰 그림

```
0단계: 기반 공사 (모든 기능의 전제)
        │
        ▼
1단계: 회사 계정과 데이터 등록 (로그인 없이는 아무것도 안 되므로 최우선)
        │
        ▼
2단계: 신청서 제출 (회사가 실제로 뭔가 "낼 수 있게")
        │
        ▼
3단계: 관리자 심사 (Letusto가 그것을 "볼 수 있게")
        │
        ▼
4단계: 소통 보조 기능 (추가자료요청, 내부메모, 담당자배정, 알림)
        │
        ▼
5단계: 다듬기 (대시보드, 관리자 부가기능)
```

**중요한 원칙: 1~3단계가 끝나야 "신청서 하나가 접수되어 심사받는" 전체 흐름이 처음으로 눈에 보입니다.** 그전까지는 부분부분만 만들어져서 실제로 써볼 수 없습니다. 그래서 Claude Code에게 작업을 맡길 때도 "이 조각까지 만들면 처음부터 끝까지 한 번 테스트해볼 수 있다"는 지점을 명확히 표시했습니다(아래 목록의 ⭐ 표시).

# 2. Claude Code 전달용 개발 명세서 목록 (Phase 1)

아래는 실제로 만들 명세서 파일의 목록입니다. 번호 순서대로 Claude Code에게 넘기는 것을 권장하며, 각 명세서는 **이전 명세서가 완료된 상태를 전제로** 작성합니다(한 번에 몰아서 만들지 않기 위함 — 앞서 마케팅 사이트 작업에서 적용한 방식과 동일합니다).

## 0단계 — 기반 공사

**명세서 00. 프로젝트 기반 설정**
- 담을 내용: 인증(로그인) 체계의 기본 골격, 외부 포털/관리자 포털 URL 및 코드 구조 분리, 공통 UI 컴포넌트(마케팅 사이트의 DESIGN.md 스타일 재사용 여부 결정), 데이터베이스 연결 기본 골격, 환경변수 관리 방식
- 완료 기준: 회원가입 없이도 "로그인 필요" 안내 화면과 관리자/외부 포털의 서로 다른 진입 URL이 동작

## 1단계 — 계정과 데이터

**명세서 01. 회사 회원가입 · 로그인 · 소속 사용자 관리**
- 대상: `08_주요화면과AC.md`의 화면 1, 2, 로그인/비밀번호재설정
- 담을 내용: Company/CompanyUser 데이터 구조(`07_데이터모델.md` 1~2번), 회원가입·로그인·초대 흐름, 이메일 인증
- 완료 기준: 담당자가 가입 → 이메일 인증 → 로그인 → 동료 초대까지 혼자서 완료 가능

**명세서 02. 브랜드 · 제품 등록 (이미지·인증서 업로드 포함)**
- 대상: 화면 6, 7
- 담을 내용: Brand/Product/ProductImage/ProductCertificate 구조, 파일 업로드 처리(`09_알림및문서관리규칙.md` Part 2 규칙 반영), 접근 제어(`10_보안과권한요구사항.md` 4번)
- 완료 기준: 브랜드 등록 → 제품 등록 → 이미지·인증서 첨부까지 완료되고, 다른 회사 계정으로 로그인해도 이 데이터가 전혀 보이지 않음(교차 테스트 필수)

## 2단계 — 신청 제출

**명세서 03. 신청서 작성 · 제출 · 현황 확인 (회사 측) ⭐**
- 대상: 화면 8~11
- 담을 내용: Application/ApplicationProduct 구조(`07_데이터모델.md` 핵심 구조), 상태값(`06_상태값정의.md` 1·2번), 제품 선택 UI, 자가진단 재확인, 제출 후 잠금 처리
- 완료 기준: 여기까지 완성되면 회사 계정으로 "신청서를 내고 상태를 확인"하는 흐름 전체가 처음으로 눈에 보입니다. 아직 관리자가 심사할 수는 없지만, 회사 쪽 경험은 완결됩니다.

## 3단계 — 관리자 심사

**명세서 04. 관리자 로그인 · 신청 목록 · 회사 관리**
- 대상: 화면 13, 15, 17
- 담을 내용: StaffUser/Role 구조(`07_데이터모델.md`, `02_사용자유형과권한표.md`), 관리자 전용 로그인 경로, 목록·필터·검색
- 완료 기준: 내부 직원 계정으로 로그인해 지금까지 들어온 신청서 목록을 확인 가능

**명세서 05. 신청서 심사 (제품별 독립 심사 + 자동 집계) ⭐**
- 대상: 화면 16의 핵심 부분
- 담을 내용: 제품별 승인/보류/반려 처리, 신청 상태 자동 집계 로직(`06_상태값정의.md`의 자동 집계 규칙을 정확히 구현하는 것이 이 명세서의 핵심), 심사 결과 확정 시 이메일 발송 연동
- 완료 기준: **여기까지 완성되면 Phase 1의 핵심 목표("신청 접수부터 심사 결과 통보까지")가 처음부터 끝까지 동작합니다.** 이 지점이 Phase 1의 진짜 마일스톤입니다.

## 4단계 — 소통 보조 기능

**명세서 06. 추가 자료 요청**
- 대상: 화면 10, 그리고 화면 7의 회신 처리
- 담을 내용: AdditionalInfoRequest 구조, 상태 전이(`06_상태값정의.md` `추가자료요청`↔`재검토중`), 회신 첨부파일 처리

**명세서 07. 내부 메모 · 담당자 배정**
- 대상: 화면 11, 12
- 담을 내용: ReviewNote/Assignment 구조, 외부 노출 완전 차단(개발 완료 후 반드시 별도로 "외부 계정으로 접근 시도" 테스트 진행), 배정 알림

**명세서 08. 이메일 알림 시스템 전체 연동**
- 대상: `09_알림및문서관리규칙.md` Part 1 전체 이벤트
- 담을 내용: 지금까지 만든 각 기능에 흩어져 있던 알림 발송 로직을 점검하고, 문서에 정의된 전체 이벤트 목록과 실제 구현이 빠짐없이 일치하는지 확인. 이메일 템플릿 관리 화면(화면 20) 포함
- 완료 기준: `09_알림및문서관리규칙.md`의 표에 있는 11개 이벤트가 모두 실제로 발송되는지 하나씩 테스트

## 5단계 — 다듬기

**명세서 09. 대시보드 (회사·관리자 양쪽)**
- 대상: 화면 3, 14
- 담을 내용: 각 포털의 첫 화면. 지금까지 만든 데이터를 요약해서 보여주는 조회 전용 화면이므로 가장 나중에 만들어도 무방

**명세서 10. 직원 관리 · 활동 로그(최소 버전)**
- 대상: 화면 18, 19
- 담을 내용: Super Admin의 직원 계정 생성/역할 부여, ActivityLog 최소 구현(상태 변경 이력 조회)

# 3. Phase 2·3 명세서는 언제 작성하나

Phase 1이 실제로 배포되고, 최소 1건의 신청이 접수부터 심사까지 완주한 뒤에 Phase 2 명세서를 작성하는 것을 권장합니다. 이유는 두 가지입니다.

1. 실제 운영 경험 없이 "샘플 요청은 이렇게 흘러갈 것이다"라고 지금 상세히 정해봐야, Phase 1을 써본 뒤 생각이 바뀔 가능성이 높습니다.
2. Phase 1 개발 과정에서 데이터 모델(`07_데이터모델.md`)이 실제로 어떻게 구현됐는지에 따라 Phase 2 설계가 미세하게 달라질 수 있습니다.

Phase 2 착수 시점에는 이 문서의 1~2번과 같은 형식(우선순위 → 명세서 목록)으로 별도 작성해 드리는 것을 제안합니다.

# 4. 명세서를 실제 프롬프트로 바꿀 때 포함해야 할 공통 요소

각 명세서를 Claude Code에게 넘기는 실제 프롬프트로 만들 때는, 아래 요소를 항상 포함하는 것을 권장합니다(마케팅 사이트 작업에서 쓴 방식과 동일한 틀입니다).

- 이 작업이 전체 시스템에서 어디에 해당하는지 (이 문서의 몇 단계인지)
- 관련된 `06_상태값정의.md`, `07_데이터모델.md`의 해당 부분을 직접 인용
- `08_주요화면과AC.md`의 완료 조건 체크리스트를 그대로 포함
- `10_보안과권한요구사항.md`의 관련 항목(특히 데이터 격리)을 명시적으로 재강조
- "이번 작업에서 하지 않을 것" — 다음 단계에서 만들 기능을 미리 만들지 않도록 범위를 명확히 제한

이렇게 하면 Claude Code가 매번 이 기획서 전체를 다시 읽지 않아도, 각 명세서 자체가 필요한 맥락을 충분히 담게 됩니다.
