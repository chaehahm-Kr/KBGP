# 1. 이 제품은 무엇인가

**K Select Network 운영 플랫폼**은 한국 K-Beauty 제조사·브랜드가 미국 시장에 진출하기 위해 Letusto Inc.와 파트너십을 맺는 전 과정을 온라인으로 처리하는 B2B 시스템입니다.

지금까지는 이 과정이 이메일과 PDF 소개서, 수작업 스프레드시트로 이루어졌습니다(신청 이력 자체가 아직 없는 초기 단계입니다). 이 시스템은 "신청 → 심사 → 샘플 → 견적 → 계약 → 발주(PO) → 생산·검사·배송 → 미국 입고"까지 이어지는 흐름을 하나의 플랫폼 안에서 추적 가능하게 만듭니다.

# 2. 왜 만드는가 (문제 정의)

| 지금 겪는 문제 | 이 시스템이 해결하는 방식 |
|---|---|
| 신청자가 이메일로 문의하면 담당자가 수작업으로 자격을 확인해야 한다 | 회사·브랜드·제품 정보를 구조화된 폼으로 받아, 심사 기준에 맞춰 화면에서 바로 검토 |
| 신청 건이 늘어나면 엑셀로는 "누가 어느 단계인지" 추적이 어려워진다 | 신청서·제품마다 명확한 상태값을 두고, 담당자 배정과 진행 이력을 시스템이 기록 |
| 샘플 발송, 견적, PO가 각각 다른 채널(이메일, 카톡, 엑셀)에 흩어진다 | 하나의 신청 건 아래에서 샘플→견적→계약→PO가 순서대로 연결되어 이력이 남는다 |
| 생산·검사·배송 상태를 브랜드사에 일일이 전화·이메일로 안내해야 한다 | 브랜드사가 로그인해서 자기 주문의 현재 상태를 직접 확인 가능 |
| 담당 직원이 바뀌거나 늘어나면 인수인계가 어렵다 | 내부 메모, 담당자 배정, 활동 이력이 시스템에 남아 누가 봐도 히스토리를 알 수 있다 |

# 3. 이 시스템이 아닌 것 (범위 밖)

명확히 선을 긋지 않으면 기획이 계속 늘어나므로, 처음부터 아닌 것을 정합니다.

- **결제 시스템이 아닙니다.** 카드 결제, 에스크로, PG 연동을 하지 않습니다. "결제 완료로 표시" 정도의 상태 기록만 합니다.
- **재고관리(WMS) 시스템이 아닙니다.** 창고 내 재고 위치, 피킹, 재고 실사는 다루지 않습니다. "미국 창고에 입고됨"이라는 상태까지만 추적합니다.
- **회계 시스템이 아닙니다.** 세금계산서, 장부 처리는 하지 않습니다. Invoice 문서를 발행·보관은 하지만 회계 처리와는 별개입니다.
- **마케팅 사이트가 아닙니다.** 프로그램 소개, 카피, 신뢰도 구축은 이미 존재하는 `www.kselectnetwork.com` 마케팅 사이트의 몫이고, 이 시스템은 로그인 이후의 실제 업무 처리 영역입니다.

# 4. 핵심 사용자 그룹 (상세는 `02_사용자유형과권한표.md`)

1. **한국 브랜드사 담당자** — 회사·브랜드·제품을 등록하고 신청서를 제출하는 사람
2. **Letusto 내부 직원** — 신청을 심사하고, 파트너십을 진행시키는 사람
3. **(Phase 3) 미국 리테일러 담당자** — 선정된 제품을 매장에서 주문·재주문하는 사람

# 5. 성공 기준 (이 시스템이 잘 작동한다는 것을 어떻게 아는가)

Phase 1 기준으로 다음을 목표로 삼습니다. 숫자는 초안이며, 실제 운영을 시작하면서 조정하는 것을 권장합니다.

- 신청서 제출부터 1차 심사 결과 안내까지 걸리는 시간이 **평균 5영업일 이내**
- 신청 상태를 확인하기 위해 브랜드사가 이메일로 문의하는 빈도가 **런칭 후 3개월 내 눈에 띄게 감소**
- 내부 담당자가 "이 신청 건이 지금 어느 단계인지"를 확인하는 데 걸리는 시간이 **엑셀 검색 없이 즉시**
- 심사 탈락/보류 사유가 시스템에 기록되어, 같은 회사가 재신청할 때 이전 이력을 바로 참고 가능

# 6. 설계 원칙

이후 모든 문서에서 반복적으로 적용하는 원칙입니다.

1. **신청서와 제품 심사는 독립적으로 움직인다.** 신청서 하나에 제품이 5개 있으면, 2개는 승인되고 3개는 보류될 수 있습니다. (확정 답변 반영)
2. **회사 → 브랜드 → 제품의 3단 구조를 처음부터 갖춘다.** 지금은 대부분 한 회사가 브랜드 하나만 가지고 있어도, 구조 자체는 1:N:N을 지원해야 나중에 데이터를 옮기지 않아도 됩니다. (확정 답변 반영)
3. **외부 화면과 내부 화면은 코드 수준에서부터 분리한다.** 브랜드사 담당자가 실수로라도 Letusto 내부 메모나 다른 회사의 정보를 볼 수 있는 구조를 원천적으로 만들지 않습니다.
4. **작은 조직에서 시작하지만 역할 기반 권한을 처음부터 설계한다.** 지금은 1~3명이 모든 역할을 겸임하지만, 시스템 안에서는 "심사자", "영업 담당", "운영 담당" 역할을 구분해 부여합니다. 사람이 늘어날 때 코드를 바꾸지 않고 역할만 추가 배정하면 되도록 합니다.
5. **모든 상태 변경과 문서는 이력을 남긴다.** 나중에 "누가 언제 이 신청을 승인했는가"를 반드시 추적할 수 있어야 합니다.
6. **Phase 1은 의도적으로 좁게 잡는다.** 심사까지만 완성해서 실제로 신청을 받아보고, 그 경험을 바탕으로 Phase 2(샘플·견적·PO)를 설계합니다. 처음부터 전체를 만들면 실제 업무와 맞지 않는 부분을 나중에 크게 고쳐야 하는 위험이 있습니다.

# 7. 기술 관련 언급에 대한 안내

이 문서 세트는 의도적으로 기술 스택(어떤 프로그래밍 언어·데이터베이스 제품을 쓸지)을 다루지 않습니다. "핵심 데이터베이스 엔터티와 관계"(`07_데이터모델.md`)는 데이터를 어떤 덩어리로 나누고 서로 어떻게 연결되는지에 대한 **개념 설계**이며, 특정 데이터베이스 제품의 문법이나 코드가 아닙니다. 실제 기술 스택 선정과 코드 작성은 이 기획서가 확정된 다음, `11_개발우선순위와개발명세서목록.md`를 바탕으로 Claude Code와 별도로 진행하시면 됩니다.
