# 용어 안내

- **역할(Role)**: "이 사람이 시스템에서 무엇을 할 수 있는가"를 정의한 이름표입니다. 한 사람이 역할을 여러 개 가질 수 있습니다. 예: 지금은 담당자 한 명이 "심사 담당"과 "영업 담당" 역할을 동시에 가질 수 있습니다.
- **권한(Permission)**: "읽기만 가능", "수정 가능", "승인 가능"처럼 더 세밀한 단위의 허용 범위입니다. 역할은 여러 권한의 묶음입니다.
- 왜 지금(1~3명)도 역할을 나누냐면, 나중에 사람이 늘어날 때 **코드를 다시 만들 필요 없이 역할만 새로 배정**하면 되기 때문입니다.

# A. 외부 사용자 (Letusto 소속이 아닌 사람)

## A-1. 회사 관리자 (Company Admin)

| 항목 | 내용 |
|---|---|
| 소속 | 한국 K-Beauty 제조사/브랜드사 |
| 이 역할은 누구인가 | 회사를 대표해서 계정을 처음 만든 사람. 보통 대표자 또는 해외영업 책임자 |
| 볼 수 있는 화면 | 자기 회사 전용 포털 전체 (05번 문서 참조) |
| 할 수 있는 것 | 회사 프로필 관리, 회사 소속 사용자 초대·삭제·권한 변경, 브랜드 등록/수정, 제품 등록/수정, 신청서 작성·제출, 신청 상태 확인, Letusto와의 메시지, (Phase 2+) 샘플 요청 확인, 견적 확인·승인, 계약서 확인, PO 확인 |
| 할 수 없는 것 | 다른 회사의 어떤 정보도 볼 수 없음. Letusto 내부 메모·심사 코멘트를 볼 수 없음. 시스템 전역 설정 변경 불가 |
| 회사당 인원 | 보통 1명이지만, 여러 명이 이 역할을 가질 수 있음(공동대표 등 대비) |

## A-2. 회사 담당자 (Company Staff)

| 항목 | 내용 |
|---|---|
| 소속 | 한국 K-Beauty 제조사/브랜드사 |
| 이 역할은 누구인가 | 회사 관리자가 초대한 실무 담당자. 해외영업팀 직원 등 |
| 할 수 있는 것 | 브랜드/제품 등록·수정, 신청서 작성(제출은 Company Admin 승인 후 가능하도록 설정 권장 — Phase 1에서는 단순화를 위해 담당자도 직접 제출 가능하게 하고 Phase 2에서 승인 단계 추가 검토), 신청 상태 확인, 메시지 주고받기 |
| 할 수 없는 것 | 회사 소속 사용자 초대/삭제 불가, 계약서 최종 승인 권한 없음(Phase 2+), 회사 프로필의 법적 정보(사업자등록번호 등) 수정 불가 — Company Admin만 가능 |

> **확인 필요:** Phase 1에서는 구분을 단순하게(Admin/Staff 2단계) 시작하고, 실제 사용 패턴을 보고 Phase 2에서 세분화(예: 재무 담당자만 계약·PO 승인 가능)할지 결정하는 것을 권장합니다.

# B. 내부 사용자 (Letusto 소속)

지금은 1~3명이 아래 역할을 겸임합니다. 시스템은 역할을 나눠 부여하되, 실제로는 한 사람이 여러 역할을 동시에 가지면 됩니다.

## B-1. 총괄 관리자 (Super Admin)

| 항목 | 내용 |
|---|---|
| 할 수 있는 것 | 아래 모든 내부 역할의 권한 + 직원 계정 생성/삭제/역할 부여, 시스템 설정(이메일 템플릿, 심사 기준 항목 등), 전체 데이터 열람 |
| 용도 | 대표자 또는 시스템 관리 책임자. Phase 1에서는 사실상 요청자 본인이 이 역할 |

## B-2. 심사 담당 (Reviewer)

| 항목 | 내용 |
|---|---|
| 할 수 있는 것 | 신청서 열람·심사(승인/보류/반려), 제품별 심사(승인/보류/반려), 추가 자료 요청, 내부 메모 작성, 회사·제품 정보 열람 |
| 할 수 없는 것 | 직원 계정 관리 불가, 시스템 설정 변경 불가 |
| Phase 1 필수 여부 | 필수 — Phase 1의 핵심 역할 |

## B-3. 영업/파트너십 담당 (Account Manager)

| 항목 | 내용 |
|---|---|
| 할 수 있는 것 | 담당 회사 배정받기, 상담 미팅 예약·관리(Phase 2), 샘플 요청 처리(Phase 2), 견적 작성·발송(Phase 2), 계약서 관리(Phase 2), 회사와의 메시지 |
| 할 수 없는 것 | 제품 심사 승인 권한은 기본적으로 Reviewer 역할이 있어야 함(한 사람이 두 역할을 겸임하는 것은 가능) |
| Phase 1 필수 여부 | Phase 2부터 실질적으로 사용. Phase 1에서는 역할만 만들어두고 담당자 배정 기능에 사용 |

## B-4. 운영 담당 (Operations Manager)

| 항목 | 내용 |
|---|---|
| 할 수 있는 것 | PO 작성·발행(Phase 2), 생산·검사·출고·배송 상태 업데이트(Phase 3), 문서(Invoice·Packing List·BOL) 업로드·관리(Phase 3), 결제 상태 업데이트(Phase 3) |
| Phase 1 필수 여부 | Phase 2~3부터 실질적으로 사용 |

## B-5. (선택) 경영진 열람 전용 (Executive Viewer)

| 항목 | 내용 |
|---|---|

| 용도 | 투자자·경영진에게 진행 현황을 보여줄 때. Phase 2 이후 필요 시 추가. Phase 1에서는 만들지 않아도 무방 |

# D. 왜 이렇게 나눴는가 — 설계 이유

**Company Admin과 Company Staff를 나눈 이유:** 회사 안에서도 "이 사람이 나가면 계정 전체가 마비된다"는 상황을 막기 위해서입니다. Admin이 여러 명일 수 있게 하면, 담당자가 퇴사해도 회사가 계정을 계속 쓸 수 있습니다.

**내부 역할을 Reviewer/Account Manager/Operations로 나눈 이유:** 지금은 한 명이 다 하더라도, "심사"와 "영업"을 같은 사람이 하면 이해상충 소지가 있습니다(심사자가 특정 브랜드를 밀어주고 싶어질 수 있음). 역할을 코드 레벨에서 분리해두면, 나중에 조직이 커졌을 때 "이 사람은 심사만, 저 사람은 영업만"으로 자연스럽게 나눌 수 있습니다. 지금 당장은 한 사람이 두 역할을 동시에 배정받으면 됩니다.

**내부 메모를 외부 사용자에게 완전히 숨긴 이유:** 심사 과정에서 나오는 솔직한 평가("이 성분표는 재검토 필요" 등)가 브랜드사에 그대로 노출되면 관계가 상할 수 있습니다. 공식적으로 전달할 내용은 "추가 자료 요청" 기능을 통해 별도로 전달합니다.
