# 이 문서에 대한 안내

**엔터티(Entity)**란 시스템이 기억해야 할 "정보 덩어리"입니다. 예를 들어 "회사"라는 엔터티는 회사명, 사업자등록번호, 주소 같은 정보를 하나로 묶어놓은 것입니다. 실제로는 데이터베이스의 "표(테이블)" 하나가 되지만, 이 문서에서는 표 이름과 열 이름 정도만 다루고, 실제 데이터베이스 제품(예: PostgreSQL)에 어떻게 만들지는 다루지 않습니다. 그건 Claude Code와 개발 단계에서 결정할 일입니다.

관계 표기: `1:N`은 "하나가 여럿을 가질 수 있다"(예: 회사 하나에 브랜드 여러 개), `N:M`은 "여러 개가 서로 여러 개씩 연결된다"(예: 신청서 하나에 제품 여러 개, 제품 하나가 여러 신청서에 등장 가능)를 뜻합니다.

# 1. 전체 관계 지도 (개략도)

```
Company (회사) ──1:N──► CompanyUser (회사 소속 사용자)
      │
      ├──1:N──► Brand (브랜드)
      │              │
      │              └──1:N──► Product (제품)
      │                             │
      │                             ├──1:N──► ProductImage (제품 이미지)
      │                             └──1:N──► ProductCertificate (인증서)
      │
      └──1:N──► Application (신청서)
                     │
                     ├──1:N──► ApplicationProduct (신청서 안의 제품별 심사) ◄──N:1── Product
                     │              │
                     │              └──1:N──► ReviewNote (내부 메모, 이 제품·신청 관련)
                     │
                     ├──1:N──► AdditionalInfoRequest (추가자료요청)
                     ├──1:N──► Assignment (담당자 배정 이력)
                     ├─1:N──► Meeting (상담 예약, Phase 2)
                     └─1:N──► Conversation (대화 스레드, Phase 2) ──1:N──► Message ──1:N──► Attachment


ApplicationProduct (승인된 것만 아래로 이어짐, Phase 2)
      │
      ├──1:N──► Sample (샘플) ──1:N──► SampleEvaluation (평가)
      │
      └──1:N──► QuoteLineItem ◄──N:1── Quote (견적) ──1:1(선택)──► Contract (계약서)
                                              │
                                              ▼
                                        PurchaseOrder (PO) ──1:N──► POLineItem
                                              │
                                              └──1:1──► Fulfillment (이행 추적, Phase 3)
                                                              │
                                                              ├──1:N──► ShippingDocument (Invoice/Packing List/BOL)
                                                              └──1:N──► Payment (결제 상태 기록)


StaffUser (Letusto 내부 직원) ──N:M──► Role (역할)
Company / Application / Sample / Quote / PO / Fulfillment 등 대부분의 엔터티 ──N:1──► ActivityLog (변경 이력)

(Phase 3)
Retailer (미국 매장) ──1:N──► RetailerUser
Retailer ──1:N──► RetailerOrder ──N:M──► Product
```

# 2. 엔터티별 설명

## Company (회사)
한국 K-Beauty 제조사·브랜드사 1곳. 회사명, 사업자등록번호, 국가, 대표 연락처, 생산 캐파 요약, 인증 현황 요약, 회사 소개, 상태(활성/비활성) 등을 가집니다.

## CompanyUser (회사 소속 사용자)
Company에 속한 로그인 계정. 이름, 이메일, 역할(Admin/Staff), 소속 Company를 가집니다. **한 사람이 두 회사에 동시에 속할 수는 없습니다** — 이렇게 해야 "다른 회사 정보가 실수로 보이는" 사고를 구조적으로 막을 수 있습니다.

## Brand (브랜드)
Company에 속한 브랜드. 브랜드명, 브랜드 소개, 로고 이미지. **회사 하나에 브랜드 여러 개** (확정 답변 반영).

## Product (제품)
Brand에 속한 개별 제품. 제품명, 카테고리(K-스킨케어 등), 용량, 가격대, 성분 정보, 상태(등록됨/판매중/단종). **브랜드 하나에 제품 여러 개.**

## ProductImage / ProductCertificate
Product에 딸린 첨부파일. 이미지는 여러 장, 인증서는 종류별(FDA 등록, 성분 인증, 상표권 등)로 여러 개 첨부 가능.

## Application (신청서)
Company가 제출하는 신청 1건. 제출일, 신청 상태(`06_상태값정의.md` 1번), 담당자, 신청 사유/메모. **회사 하나가 여러 신청서를 낼 수 있음** (예: 시기를 달리해 재신청).

## ApplicationProduct (신청서 안의 제품 — 핵심 연결 고리)
"이 신청서에 이 제품이 포함되어 있고, 이 제품은 이런 심사 상태다"를 나타내는 연결 엔터티입니다. **이 시스템에서 가장 중요한 엔터티 중 하나**입니다 — 신청 상태와 제품 심사 상태가 독립적이라는 확정 답변이 바로 이 구조로 구현됩니다. 제품 심사 상태(`06_상태값정의.md` 2번), 심사 사유, 심사일, 심사자를 가집니다.

왜 Product에 직접 심사 상태를 넣지 않고 ApplicationProduct라는 별도 엔터티를 만들었는지: 같은 제품이 신청서 A에서는 반려됐다가, 나중에 개선되어 신청서 B에서는 승인될 수 있습니다. 심사 상태를 Product에 직접 붙이면 이 히스토리가 사라집니다.

## ReviewNote (내부 메모)
Application 또는 ApplicationProduct에 딸린 메모. 작성자(StaffUser), 작성일, 내용. **외부 사용자에게는 절대 노출되지 않음.**

## AdditionalInfoRequest (추가 자료 요청)
Application에 딸린 요청 건. 요청 내용, 요청일, 회사의 회신 내용, 회신 첨부파일, 처리 상태(대기중/회신완료).

## Assignment (담당자 배정)
Application과 StaffUser를 연결. 배정일, 배정한 사람, 배정 사유. 이력으로 여러 건 쌓일 수 있음(담당자 변경 시마다 새 레코드).

## Meeting (상담 예약, Phase 2)
Application 또는 Company에 딸린 미팅. 일시, 참석자, Microsoft Bookings 연동 ID, 상태(예정/완료/취소).

## Conversation / Message / Attachment (Phase 2)
Application 또는 ApplicationProduct 단위로 열리는 대화방. Message는 발신자, 내용, 발신 시각. Attachment는 Message에 딸린 파일.

## Sample (샘플, Phase 2)
ApplicationProduct에 딸린 샘플 요청 건. 요청 수량, 배송지, 운송장번호, 상태(`06_상태값정의.md` 3번).

## SampleEvaluation (샘플 평가, Phase 2)
Sample에 딸린 평가 기록. 평가자, 평가 결과, 코멘트, 평가일.

## Quote (견적, Phase 2) / QuoteLineItem
Application(또는 여러 ApplicationProduct 묶음) 단위로 발행되는 견적. 견적번호, 유효기간, 상태(`06_상태값정의.md` 4번). QuoteLineItem은 견적 안의 제품별 수량·단가 한 줄.

## Contract (계약서, Phase 2)
Quote 승인 후 생성. 계약서 파일(PDF), 서명 상태(회사측 서명 여부, Letusto측 서명 여부), 체결일.

## PurchaseOrder (PO, Phase 2) / POLineItem
Letusto가 발행 주체, Company(공급사)가 대상. PO번호, 발행일, 상태(`06_상태값정의.md` 5번), 결제 조건(문서 기록용). POLineItem은 PO 안의 제품별 수량·단가·납기.

## Fulfillment (이행 추적, Phase 3)
PurchaseOrder 1건에 대응하는 이행 상태 묶음. 상태(`06_상태값정의.md` 6번), 각 단계 진입일(생산시작일, 검사일, 출고일 등), 예상 미국 입고일, 실제 입고일.

## ShippingDocument (Phase 3)
Fulfillment에 딸린 문서. 문서 종류(Invoice/Packing List/BOL/기타), 파일, 발행일.

## Payment (결제 상태, Phase 3)
Fulfillment 또는 PO에 딸린 결제 상태 기록. 결제 조건, 상태(미결제/일부결제/완결제 — 시스템은 상태만 기록, 실제 이체는 외부), 기록일, 기록자, 참고 메모(예: "송금 확인, 은행 참조번호 XXXX").

## StaffUser / Role (내부 직원 및 역할)
`02_사용자유형과권한표.md`의 5개 역할(Super Admin, Reviewer, Account Manager, Operations, Executive Viewer)을 코드화한 것. 한 StaffUser가 여러 Role을 가질 수 있음(N:M).

## ActivityLog (변경 이력)
"누가, 언제, 무엇을, 어떻게 바꿨는가"를 기록하는 공통 로그. 대부분의 엔터티(Application, ApplicationProduct, Quote, PO, Fulfillment 등)의 상태 변경마다 하나씩 쌓입니다. 대상 엔터티 종류, 대상 ID, 변경 전 상태, 변경 후 상태, 변경자, 변경 시각, 사유(있는 경우).

## Retailer / RetailerUser / RetailerOrder (Phase 3)
미국 Beauty Supply 매장. Company/CompanyUser와 구조는 비슷하지만 완전히 다른 엔터티로 분리합니다(한국 브랜드사와 미국 리테일러는 보는 정보와 권한이 근본적으로 다르므로). RetailerOrder는 Fulfillment와 유사한 구조를 갖되 리테일러 관점의 주문입니다.

# 3. 왜 이렇게 나눴는가 — 핵심 설계 판단 3가지

**① ApplicationProduct를 독립 엔터티로 뽑은 것.** 신청서·제품·심사상태를 어떻게 연결할지가 이 시스템 전체에서 가장 중요한 결정이었습니다. Product에 상태를 직접 붙이면 재신청 히스토리가 사라지고, Application에만 상태를 두면 "제품별로 따로 심사"가 불가능합니다. ApplicationProduct라는 중간 엔터티가 두 확정 답변(회사:브랜드:제품 = 1:N:N, 신청 상태와 제품 심사 상태는 독립적)을 동시에 만족시키는 유일한 방법입니다.

**② PO의 방향을 Letusto → Company로 잡은 것.** "직접 매입 후 재판매" 답변에 따라, PurchaseOrder의 발행자는 Letusto이고 수신자(공급사 확인 주체)는 Company입니다. 만약 나중에 Letusto가 미국 리테일러에게 파는 쪽 주문서(Sales Order)도 시스템에 넣고 싶어지면, PurchaseOrder와는 별도의 엔터티(예: SalesOrder)로 Phase 3에서 추가하는 것을 권장합니다. 지금 단계에서는 원 요청에 없으므로 설계에 포함하지 않았습니다.

**③ Retailer를 Company와 완전히 분리한 것.** 이름이 비슷해서 하나로 합치고 싶을 수 있지만, 한국 브랜드사(공급자)와 미국 매장(구매자)은 방향이 반대입니다. 하나의 엔터티로 합치면 나중에 "이 사람이 판매자인지 구매자인지"를 매번 조건문으로 구분해야 하는 복잡함이 생깁니다. Phase 3에서 실제로 설계할 때도 이 원칙을 유지하는 것을 권장합니다.
