# 이 문서의 범위에 대한 안내

**Acceptance Criteria(수용 기준, 이하 AC)**란 "이 기능이 완성됐다고 인정하려면 무엇이 되어야 하는가"를 구체적으로 적은 체크리스트입니다. Claude Code가 개발할 때 "다 만들었다"의 기준이 되고, 테스트할 때도 이 목록을 그대로 확인하면 됩니다.

Phase 1(MVP)에 포함된 화면은 **전부 상세 AC**를 적었습니다. Phase 2·3 화면은 **이름과 한 줄 설명만** 적었습니다 — 지금 상세 설계를 해봐야 Phase 1 운영 경험 없이는 추측에 가깝고, 오히려 나중에 다시 뒤집을 가능성이 커서 낭비입니다. Phase 2 착수 시점에 이 문서와 같은 형식으로 별도 작성하는 것을 권장합니다.

# Part 2 — 상세 AC (핵심 12개 화면)

아래 형식을 모든 화면에 동일하게 적용합니다: **사용자 / 목적 / 입력값 / 관련 상태값 / 권한 / 알림 / 예외 상황 / Acceptance Criteria**

---

## 1. 회원가입 (Company Admin 생성)

- **사용자**: 아직 계정이 없는 한국 브랜드사 담당자 (가입 후 자동으로 Company Admin이 됨)
- **목적**: 회사 계정과 첫 사용자 계정을 동시에 생성해 플랫폼 사용을 시작한다
- **입력값**: 회사명, 사업자등록번호, 국가, 담당자 이름, 담당자 이메일, 담당자 연락처, 비밀번호, 이용약관 동의 여부
- **관련 상태값**: 없음(Company 생성 시 기본 상태는 `활성`)
- **권한**: 로그인 불필요(누구나 접근 가능한 화면)
- **알림**: 가입 완료 시 입력한 이메일로 인증 메일 발송. 관리자에게는 "신규 회사 가입" 알림(선택사항, 실시간 알림보다 대시보드 표시로 충분)
- **예외 상황**:
  - 이미 등록된 이메일로 가입 시도 → "이미 사용 중인 이메일입니다" 안내, 로그인 페이지로 유도
  - 사업자등록번호 형식 오류 → 형식 안내와 함께 재입력 요청
  - 이메일 인증을 완료하지 않고 24시간 경과 → 미인증 계정으로 표시, 로그인 시 인증 재발송 안내
- **Acceptance Criteria**:
  - [ ] 필수 항목을 모두 채우지 않으면 제출 버튼이 비활성화되거나 제출 시 항목별 오류 메시지가 표시된다
  - [ ] 가입 완료 즉시 Company와 CompanyUser(역할: Admin) 레코드가 함께 생성된다
  - [ ] 이메일 인증 전에는 로그인은 가능하되 신청서 제출 등 핵심 기능은 제한된다
  - [ ] 비밀번호는 최소 길이·조합 규칙을 만족해야 하며, 화면에 규칙이 안내된다

## 2. 소속 사용자 관리

- **사용자**: Company Admin
- **목적**: 같은 회사 소속 동료를 초대해 함께 시스템을 쓰거나, 퇴사자 계정을 정지시킨다
- **입력값**: 초대할 사용자의 이름, 이메일, 역할(Admin/Staff)
- **관련 상태값**: 초대 상태(`초대됨` → `가입완료` / `초대만료`)
- **권한**: Company Admin만 접근. Company Staff는 이 화면 자체가 보이지 않음
- **알림**: 초대받은 사람에게 이메일로 초대 링크 발송. 링크는 7일간 유효
- **예외 상황**:
  - 이미 다른 회사에 소속된 이메일을 초대 → "이미 다른 회사 계정으로 가입된 이메일입니다" 오류
  - Company Admin이 자기 자신의 Admin 권한을 스스로 회수하려 할 때, 회사에 남은 Admin이 자신뿐이면 차단(회사가 관리자 없는 상태가 되는 것을 방지)
- **Acceptance Criteria**:
  - [ ] 초대 발송 즉시 목록에 `초대됨` 상태로 표시된다
  - [ ] 초대받은 사람이 링크로 가입을 완료하면 상태가 `가입완료`로 자동 변경된다
  - [ ] 7일 내 미가입 시 상태가 `초대만료`로 바뀌고, 재초대 버튼이 노출된다
  - [ ] Admin이 다른 사용자를 삭제하면 즉시 로그인 세션이 만료되고 재로그인이 불가능해진다

## 3. 브랜드 등록·수정

- **사용자**: Company Admin, Company Staff
- **목적**: 회사가 보유한 브랜드를 시스템에 등록해, 이후 제품과 신청서에서 선택할 수 있게 한다
- **입력값**: 브랜드명, 브랜드 소개(짧은 설명), 로고 이미지(선택)
- **관련 상태값**: 없음(단순 등록 데이터. 다만 `삭제됨` 플래그로 논리 삭제 처리 권장 — 이미 신청서에 연결된 브랜드는 물리 삭제하면 안 됨)
- **권한**: 본인 소속 회사의 브랜드만 조회·수정 가능
- **알림**: 없음
- **예외 상황**:
  - 이미 신청서에 사용된 브랜드를 삭제하려 할 때 → 물리 삭제 대신 "더 이상 사용하지 않음" 처리, 기존 신청 이력은 유지
- **Acceptance Criteria**:
  - [ ] 브랜드명은 같은 회사 내에서 중복될 수 없다
  - [ ] 등록된 브랜드는 즉시 제품 등록 화면의 브랜드 선택 목록에 나타난다
  - [ ] 이미 승인된 신청서에 연결된 브랜드 정보를 수정해도, 과거 신청서에 표시되던 정보(스냅샷)는 바뀌지 않는다 — 나중에 "그때 뭐라고 써서 냈는지" 확인 가능해야 함

---

## 4. 제품 등록·수정 (이미지·인증서 업로드 포함)

- **사용자**: Company Admin, Company Staff
- **목적**: 신청서에 담을 개별 제품 정보를 구조화된 형태로 등록한다
- **입력값**: 소속 브랜드, 제품명, 카테고리(스킨케어/헤어&스칼프/뷰티소품·툴/데일리케어/웰니스·기능성패치), 용량, 소비자가(추정), 성분표(텍스트 또는 파일), 제품 이미지(최소 1장, 최대 5장), 인증서 파일(복수, 종류 태그 포함: 성분인증/상표권/FDA등록/기타)
- **관련 상태값**: 없음(제품 자체 상태가 아니라, 신청서에 포함됐을 때만 `ApplicationProduct` 상태가 생김 — `06_상태값정의.md` 참고)
- **권한**: 본인 소속 회사의 제품만 조회·수정 가능
- **알림**: 없음
- **예외 상황**:
  - 이미지 파일 형식·용량 초과 시 → 허용 형식(JPG/PNG)과 최대 용량(예: 10MB) 안내 후 업로드 거부
  - 이미 심사가 완료(승인/반려)된 신청서에 포함된 제품의 정보를 수정하려 할 때 → 그 신청서의 심사 결과에는 영향 없음을 안내(과거 심사는 그 시점 정보 기준). 수정된 정보로 다시 심사받으려면 새 신청서 필요
- **Acceptance Criteria**:
  - [ ] 이미지 최소 1장, 인증서는 선택사항이지만 없을 경우 신청서 제출 시 경고(차단은 아님) 표시
  - [ ] 등록된 제품은 즉시 신청서 작성 화면의 제품 선택 목록에 나타난다
  - [ ] 업로드된 파일은 회사 소속 사용자만 접근 가능한 저장 위치에 보관되고, 직접 URL로 외부인이 접근할 수 없다 (`10_보안과권한요구사항.md` 참고)

## 5. 신청서 작성 및 제출

- **사용자**: Company Admin, Company Staff
- **목적**: 심사를 받고 싶은 제품들을 하나의 신청서로 묶어 제출한다
- **입력값**: 제품 선택(1개 이상, 여러 브랜드 제품 혼합 가능), 신청 동기·메모(자유 텍스트, 선택), 참여 조건 자가진단 6개 항목 재확인 체크(마케팅 사이트의 자가진단과 동일 항목)
- **관련 상태값**: `임시저장` → `제출됨` (`06_상태값정의.md` 1번)
- **권한**: 본인 소속 회사 명의로만 제출 가능
- **알림**: 제출 완료 시 회사 담당자에게 확인 이메일. Letusto 내부(Reviewer 전체 또는 담당 배정 로직)에 신규 신청 알림
- **예외 상황**:
  - 참여 조건 자가진단에서 미충족 항목이 있는 상태로 제출 시도 → 제출을 막지는 않되(최종 판단은 사람이 하므로) "일부 조건 미충족" 경고를 표시하고 계속 진행할지 확인
  - 같은 제품 조합으로 이미 `심사중`인 신청서가 있는 상태에서 새 신청서 제출 시도 → 중복 안내(차단은 하지 않음, 회사가 의도적으로 재신청할 수도 있으므로)
- **Acceptance Criteria**:
  - [ ] 제품을 최소 1개 선택하지 않으면 제출 불가
  - [ ] `임시저장` 상태에서는 언제든 수정 가능하지만, `제출됨` 이후에는 회사가 직접 내용을 수정할 수 없고 "추가 자료 요청"을 통해서만 보완 가능
  - [ ] 제출 즉시 신청서 상태가 `제출됨`으로 바뀌고, 포함된 각 제품의 `ApplicationProduct` 레코드가 `검토대기` 상태로 함께 생성된다
  - [ ] 제출 후 신청번호가 자동 발급되어 회사와 관리자 양쪽 화면에 동일하게 표시된다

## 6. 신청 현황 목록 (회사 측)

- **사용자**: Company Admin, Company Staff
- **목적**: 우리 회사가 낸 신청서들의 현재 상태를 한눈에 확인한다
- **입력값**: (조회 화면이므로 입력 없음) 상태별 필터, 제출일순 정렬
- **관련 상태값**: `06_상태값정의.md` 1번 전체
- **권한**: 본인 소속 회사의 신청서만 조회
- **알림**: 없음(이 화면 자체는 알림을 발생시키지 않음)
- **예외 상황**: 신청 건이 하나도 없을 때 → "아직 제출한 신청서가 없습니다. 새 신청서 작성하기" 안내와 버튼 표시
- **Acceptance Criteria**:
  - [ ] 목록에는 신청번호, 제출일, 포함 제품 수, 신청 상태가 표시된다
  - [ ] 상태값 변경은 실시간 반영까지는 아니어도, 페이지를 새로고침하면 항상 최신 상태가 보인다
  - [ ] `추가자료요청` 상태인 건은 시각적으로 강조 표시되어(예: 색상·아이콘) 회사가 놓치지 않도록 한다

---

## 7. 신청서 상세 (회사 측 뷰)

- **사용자**: Company Admin, Company Staff
- **목적**: 신청서 하나의 상세 내용과, 포함된 각 제품의 개별 심사 상태를 확인하고, 추가 자료 요청에 대응한다
- **입력값**: (조회 위주) 추가 자료 요청이 있는 경우 회신 텍스트·첨부파일 입력
- **관련 상태값**: 신청 상태 + 포함된 각 제품의 `ApplicationProduct` 상태
- **권한**: 본인 소속 회사의 신청서만 조회. 내부 메모는 절대 노출되지 않음
- **알림**: 회신 제출 시 담당 관리자에게 알림
- **예외 상황**: 추가 자료 요청에 대한 회신 기한(예: 14일)을 넘겼을 때 → 관리자에게 "무응답" 알림, 신청서는 `보류`로 자동 전환 검토(정책은 운영하며 확정 권장)
- **Acceptance Criteria**:
  - [ ] 포함된 제품별로 개별 심사 상태와, 있는 경우 반려·보류 사유가 명확히 표시된다
  - [ ] 반려/보류 사유는 관리자가 작성한 "공식 사유"만 노출되고, 내부 메모는 어떤 경로로도 노출되지 않는다
  - [ ] 추가 자료 요청이 있으면 화면 최상단에 눈에 띄게 표시되고, 회신 폼이 바로 아래 나타난다

## 8. [관리자] 신청 목록

- **사용자**: Reviewer, Super Admin (Account Manager는 Phase 2부터 실질 사용)
- **목적**: 들어온 모든 신청서를 한눈에 보고, 우선 처리할 것을 찾는다
- **입력값**: 상태 필터, 담당자 필터, 회사명 검색, 제출일 정렬
- **관련 상태값**: `06_상태값정의.md` 1번 전체
- **권한**: 내부 직원 전체 열람 가능(회사별 제한 없음). 단 수정(심사 등)은 배정된 담당자 또는 Super Admin만
- **알림**: 신규 `제출됨` 건이 생기면 목록 상단에 강조 표시 + (선택) 이메일/슬랙 등 채널 알림
- **예외 상황**: 담당자 미배정 상태로 3일 이상 방치된 건 → 목록에서 경고 표시(SLA 관리, Phase 1에서는 표시만, 자동 에스컬레이션은 Phase 3 검토)
- **Acceptance Criteria**:
  - [ ] 기본 정렬은 "담당자 미배정 + 오래된 순"이 먼저 보이도록 한다
  - [ ] 상태별 필터를 조합해서 사용할 수 있다(예: `심사중` + `내 담당 건만`)
  - [ ] 목록에서 바로 담당자 배정이 가능하다(상세 페이지 진입 없이)

---

## 9. [관리자] 신청서 상세 — 심사

- **사용자**: Reviewer(배정된 담당자), Super Admin
- **목적**: 신청서와 포함된 각 제품을 검토해 승인/보류/반려를 결정한다
- **입력값**: 제품별 심사 결과(승인/보류/반려) + 사유(반려·보류 시 필수), 신청서 전체에 대한 종합 코멘트(선택)
- **관련 상태값**: `06_상태값정의.md` 1번, 2번 전체 — 이 화면이 두 상태값이 만나는 지점
- **권한**: 배정된 Reviewer 또는 Super Admin만 심사 가능. 배정되지 않은 다른 Reviewer는 조회는 가능하되 심사 버튼 비활성화(교차 검토를 원하면 Super Admin이 재배정)
- **알림**: 신청서 전체 상태가 확정되는 순간(승인/부분승인/보류/반려) 회사에 이메일 자동 발송
- **예외 상황**:
  - 반려·보류 선택 시 사유를 입력하지 않으면 저장 불가(강제)
  - 이미 확정된 심사 결과를 번복하려 할 때 → "재심사 사유"를 별도로 입력하게 하고, 이 액션 자체가 `ActivityLog`와 `ReviewNote`에 자동 기록됨
- **Acceptance Criteria**:
  - [ ] 제품이 5개면 5개 각각에 대해 독립적으로 승인/보류/반려를 선택할 수 있다
  - [ ] 모든 제품의 심사가 끝나면 신청서 전체 상태가 `06_상태값정의.md`의 자동 집계 규칙에 따라 자동으로 계산되어 표시된다(관리자가 별도로 "전체 승인" 버튼을 누를 필요 없음)
  - [ ] 심사 결과 저장과 동시에 회사에 이메일이 발송되고, `ActivityLog`에 변경 이력이 남는다
  - [ ] 심사 화면에서 바로 "추가 자료 요청"과 "내부 메모 작성"으로 이동할 수 있다(화면 전환 최소화)

## 10. [관리자] 추가 자료 요청

- **사용자**: Reviewer, Super Admin
- **목적**: 심사에 필요한 정보가 부족할 때 회사에 공식적으로 요청한다
- **입력값**: 요청 내용(자유 텍스트, 예: "성분표 재제출 필요"), 어느 제품에 대한 요청인지(선택, 신청서 전체에 대한 요청도 가능)
- **관련 상태값**: 신청 상태를 `추가자료요청`으로 전환
- **권한**: 배정된 담당자 또는 Super Admin
- **알림**: 요청 즉시 회사에 이메일. 회사가 회신하면 담당자에게 이메일
- **예외 상황**: 회신 기한 초과 시 처리 정책은 `7번 화면`과 동일하게 적용
- **Acceptance Criteria**:
  - [ ] 요청을 보내면 신청서 상태가 즉시 `추가자료요청`으로 바뀐다
  - [ ] 회사가 회신을 제출하면 상태가 `재검토중`으로 자동 전환되고 담당자에게 알림이 간다
  - [ ] 하나의 신청서에 여러 차례 추가 자료 요청이 가능하며, 각 요청과 회신 쌍이 이력으로 모두 보존된다

---

## 11. [관리자] 내부 메모

- **사용자**: Reviewer, Account Manager, Operations, Super Admin (내부 직원 전체)
- **목적**: 외부에 공개하지 않을 심사 판단 근거, 동료에게 남기는 인수인계 메모를 기록한다
- **입력값**: 메모 내용(자유 텍스트), 어느 신청서/제품에 대한 것인지
- **관련 상태값**: 없음(상태 변경을 일으키지 않는 순수 기록)
- **권한**: 작성은 내부 직원 누구나. 삭제는 작성자 본인 또는 Super Admin만(다른 사람 메모를 함부로 지울 수 없게)
- **알림**: 없음(다만 같은 신청서에 다른 담당자가 메모를 남기면 배정된 담당자에게 알림하는 것을 Phase 2에서 검토 가능)
- **예외 상황**: 없음
- **Acceptance Criteria**:
  - [ ] 작성한 메모는 어떤 화면·API를 통해서도 외부 사용자(Company 소속)에게 노출되지 않는다 — 이 부분은 개발 시 반드시 별도 테스트 항목으로 확인
  - [ ] 메모에는 작성자와 작성 시각이 자동으로 기록되고 수정할 수 없다(신뢰성 있는 이력을 위해 수정이 아닌 "추가"만 가능, 오류 정정 시 새 메모로 정정 사실을 남김)

## 12. [관리자] 담당자 배정

- **사용자**: Super Admin(전체 배정 권한), Reviewer(자기 자신을 담당자로 지정하는 정도는 허용 검토)
- **목적**: 신청서 하나를 특정 내부 직원의 책임으로 지정해 처리 주체를 명확히 한다
- **입력값**: 담당자로 지정할 StaffUser 선택, 배정 사유(선택)
- **관련 상태값**: 신청 상태를 `제출됨` → `배정됨`으로 전환(최초 배정 시)
- **권한**: Super Admin 전체 배정 가능. 그 외 역할은 정책에 따라 제한(1차 제안: Reviewer는 미배정 건을 자기 담당으로 가져가는 것만 허용, 남에게 넘기는 것은 Super Admin만)
- **알림**: 새로 배정된 담당자에게 이메일 또는 인앱 알림
- **예외 상황**: 담당자가 휴가·퇴사 등으로 재배정이 필요할 때 → 배정 이력이 계속 누적되어(레코드 삭제가 아니라 새 레코드 추가) "이전에 누가 담당했는지" 추적 가능
- **Acceptance Criteria**:
  - [ ] 배정 즉시 신청 목록에서 담당자 이름이 표시된다
  - [ ] 배정 변경 시 이전 담당자에게도 "배정 해제" 알림이 간다(업무 인수인계 누락 방지)
  - [ ] 담당자가 없는 상태로도 신청서 열람과 심사가 기술적으로는 가능하지만(막지는 않음), 목록에서 "미배정" 경고가 계속 표시된다
